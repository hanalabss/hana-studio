# 다눌 · 카드프레소 · 하나스튜디오 비교와 이식 로드맵

작성일: 2026-11-12

## 1. 분석 대상과 근거 수준

| 대상 | 실체 | 분석 방법 | 신뢰 수준 |
|---|---|---|---|
| 다눌 (DaNooll-PlusX 1.0.0.1) | .NET 4 WinForms. 디자이너 `DaNul-Plus.exe` + 데이터 인쇄 `DaNooll-Plus(Data).exe` | REA 메타데이터 분석 + ILSpy로 C# 전체 디컴파일 후 코드 정독 | 높음 (코드 직접 확인) |
| 카드프레소 1.7.70 | Qt 정적 링크 32비트 네이티브 단일 실행 파일(210MB) | REA PE 분석 + 내장 리소스 묶음 98개 추출(XML/UI/번역/문서 샘플) 정독 + 클래스명·로그 문자열 + R600/RTAI 인쇄 코드 Ghidra 디컴파일 | 중간 (설계·옵션은 파일로, R600/RTAI 호출은 코드로 확인. 그 밖의 내부 로직은 미확인) |
| 하나스튜디오 | Python / PySide6 | 저장소 코드 정독 | 높음 |

주의할 점:

- `VISION.DANOOL.exe`는 InstallShield 설치 파일이라 직접 풀지 못했고, PC에 설치된 `C:\Program Files (x86)\DaNooll-PlusX`(2017년 빌드)를 분석했다. 설치 파일과 같은 버전인지는 확인하지 못했다.
- 카드프레소의 R600/RTAI 플러그인이 SDK에 넘기는 실제 인자(임계값, 마그네틱 옵션, 카드 이동 위치 등)는 설정 파일에 없고 바이너리에 하드코딩되어 있다. 210MB 전체 분석은 메모리 부족으로 중단되어, R600/RTAI 관련 함수 약 180개만 Ghidra로 디컴파일해 확인했다. 결과는 `r600-sdk-reference.md`에 있다.
- SDK 함수 87개의 인자 이름과 자료형은 하나스튜디오 자체 DLL에서 확인했다. 같은 문서에 있다.
- 카드프레소 템플릿(`.cardTemplate`) 상당수는 암호가 걸린 ZIP이라 열지 않았다. 문서 형식은 암호 없는 샘플에서 확인했다.
- 두 프로그램의 코드·폰트·클립아트·템플릿·DLL은 가져오지 않는다. 기능과 설계만 참고해 새로 구현한다.

## 2. 세 프로그램 요약

### 2.1 다눌 (DaNooll-PlusX)

구조

- 객체 모델: `Card → Side(앞/뒤) → ControlObject`. 객체 10종: 텍스트, 이미지, 선, 사각형, 원, 바코드(이미지), 바코드(폰트), QR, 마그네틱, RF-IC.
- 좌표는 카드 기준 1/100인치. 기본 카드 214×340(2.14"×3.40").
- 편집: 도구 클래스 + 명령 패턴 실행취소, 정렬/동일 간격, 모눈, 눈금자, 확대/축소, 복사/붙여넣기.
- 파일: `.dnc` = `XmlSerializer`로 쓴 평문 XML. 이미지는 내장하지 않고 폴더+파일명만 저장.
- 인쇄: Windows 프린터 드라이버(`PrintDocument`)에 GDI로 그림. SDK를 쓰지 않는다(Fargo SDK는 카드 이동에만 사용).

장점

- 구조가 단순해서 전체를 이해하고 재현하기 쉽다.
- 객체에 `FieldName`만 지정하면 DB 열과 연결되는 직관적인 바인딩.
- 디자인에서 DB를 바로 생성하는 기능(필드명 지정 → MDB 생성).
- 사진 필드가 실용적이다. 레코드마다 확대율·위치를 따로 저장하고, 파일이 없는 레코드는 그리드에서 주황색으로 표시하며, 전체 사진을 한 번에 이동/확대하는 일괄 조정이 있다.
- 한/영/일/중 언어 전환.

단점 (재현하면 안 되는 것 포함)

- DB는 Access(MDB/ACCDB)만, 그것도 첫 번째 테이블만 쓴다. Excel/CSV 미지원.
- DB를 열 때 사용자 파일을 직접 고친다: 기본키 제거, 열을 `VARCHAR(255)`로 변경, `DANUL_DATA_INDEX` 자동번호 열 추가.
- SQL을 문자열로 이어 붙인다. 값에 작은따옴표가 있으면 저장이 깨진다.
- 인쇄 대상은 "선택한 행"뿐이다. 전체/범위/조건/매수 지정이 없다.
- 일괄 인쇄는 레코드당 스풀러 작업 1건. 대기 작업 3건 초과 시 대기. 취소해도 이미 스풀된 작업은 남는다. 작업 스레드에서 UI를 직접 건드린다.
- 마그네틱은 `~1%데이터?` 텍스트를 인쇄물에 그려 드라이버가 가로채 주기를 기대하는 방식이다. 검증도 없다.
- RF(Mifare)는 디자이너 단건 인쇄에서만, 한 블록만, 항상 Key A로 쓴다. 인증 실패를 성공으로 처리한다. 데이터 프로그램에서는 RF 상자가 그대로 카드에 인쇄된다.
- QR 옵션(버전/오류복원/크기) UI는 있지만 실제로는 반영되지 않는다(고정값).
- 바코드를 약 100dpi로 만든 뒤 확대해서 품질이 낮다.
- 회전 값이 저장·복제에서 누락되어 재열기나 인쇄 시 회전이 풀린다.
- 화면 단위(96/inch)와 인쇄 단위(100/inch)가 달라 표시 mm가 약 3.6% 어긋난다.
- 경로(DB, 이미지)가 모두 절대 경로라 다른 PC로 옮기면 깨진다.

### 2.2 카드프레소 1.7.70

구조

- 편집기: Qt 그래픽 씬. 항목마다 `SIDE`(앞/뒤)와 `LAYER`(컬러, 오버레이, UV, 실버, 홀로그램 등) 속성.
- 데이터 소스 개념: 모든 항목은 "소스"를 가진다. 키보드 입력, DB 열, 인쇄 카운터, 인쇄 날짜, 다른 항목 연결, 파일, 카메라/스캐너, 서명 패드, 지문, DB 이미지.
- 문서 파일: ZIP 안에 `Document/xl.xml` + 이미지 + 인코딩 스크립트. 좌표는 1/100mm.
- 프린터: 제조사별 플러그인(약 30종). 플러그인은 지원 기능·명령·설정을 XML로 선언한다.
- 하나스튜디오와 같은 Dascom R600 / RTAI SDK 플러그인이 들어 있다.

장점

- DB 연결 범위가 넓다: 문서 내장 DB, SQLite, Access, CSV, Excel, ODBC, MySQL 등 12종.
- 연결 마법사가 체계적이다: 드라이버 → DB → 테이블 → 열 선택 → 기준 열(행 식별용) → 필터 → 정렬.
- 열 데이터 형식: 한 줄 텍스트, 여러 줄, 정수, 실수, 날짜, 시간, 목록, DB 목록, DB 카운터, 사진(비율/고정 크기), 파일 참조 이미지.
- 가져오기 마법사: CSV(인코딩·구분자 자동 추정, 헤더 유무), Excel(시트 선택), Access. 파일 열과 문서 열을 끌어서 맞춘다.
- 보기 3종: 그리드(선택 인쇄), 폼(카드 미리보기 포함), 디자인 옆 미니 보기. 조건 필터와 찾기(12가지 연산자, AND/OR).
- 열 연결(concatenation): 접두/접미 + 여러 열 연결, 값이 비면 해당 접두어 숨김.
- DB 인쇄 대상 선택: 처음/현재/마지막/전체/사용자 지정(`1,3,4-9`), 그리드에서 선택한 레코드, 조건 인쇄.
- 인쇄 후 DB에 상태/횟수/날짜를 다시 기록. "전체를 인쇄됨/안 됨으로 표시" 수동 처리도 있다.
- 인쇄 작업 관리: 작업 저장소(SQLite), 작업 상태(대기/실행/성공/중단), 레코드별 진행 표시와 "이 레코드 건너뛰기".
- 카드별 작업 목록: 앞면 인쇄, 뒷면 인쇄, 마그네틱 인코딩, 접촉 인코딩, 비접촉 작업, 마그네틱 읽기를 개별로 켜고 끈다.
- 오류 정책: 작업 중단 또는 카드 배출 후 재시도(최대 3회). 마그네틱은 쓰고 나서 읽어 검증한다.
- 렌더링 옵션: K패널 처리 방식 6종, 안티앨리어싱, 180도 회전, 좌우/상하 반전, 여백.
- 바코드 1D 약 80종, 2D 10종.
- 인쇄 카운터/날짜 항목, 사용자·그룹·권한·감사 리포트, 자동 인쇄, 웹 프린트 서버.

단점

- 규모가 매우 크고 복잡하다. 전부 따라가는 것은 비현실적이다.
- 주요 기능이 에디션(XXS~XXL)과 레코드 수 제한으로 잠겨 있다. 외부 DB는 XS 이상, ODBC/MySQL은 XL 이상.
- R600/RTAI 전용 지원은 얕다. RTAI에 노출하는 고유 옵션은 UV 레이어, 실버 레이어, K패널 분리 세 가지뿐이고, 상태 조회·청소·리본 정보 도구가 없다.
- 하나스튜디오의 핵심인 AI 배경 제거와 화이트 마스크 자동 생성이 없다.
- 필터가 SQL 조각을 그대로 받는 구조다.

### 2.3 하나스튜디오

장점

- AI 배경 제거(rembg)로 화이트 마스크를 자동 생성한다. 두 프로그램 모두에 없는 기능이다.
- R600 SDK를 직접 호출한다. 드라이버·스풀러를 거치지 않아 제어 범위가 넓다.
- 도련 자르기(58×90 → 54×86), 위치 보정, 면별 방향, 양면 인쇄, 인쇄 대기열이 이미 있다.
- Supabase 기반 라이선스와 관리자 패널이 있다.
- SDK DLL에는 아직 쓰지 않는 기능(텍스트·바코드·QR 그리기, UV·화이트·블랙 레이어, 상태 조회, 마그네틱, Mifare, 접촉식 칩)이 이미 들어 있다.

단점

- 카드 디자인 편집기가 없다. 면당 이미지 1장을 카드 전체에 늘려 인쇄한다.
- 데이터 연동이 없다. "매수"만 있고 가변 데이터 인쇄가 없다.
- 디자인 파일 저장/열기, 내보내기가 없다(관련 함수는 있으나 호출되지 않는다).
- 프린터 상태·리본 잔량·오류 문구가 없다. 오류는 DLL 반환 코드 숫자로만 나온다.
- 대기열 취소 버튼이 없고, 인쇄 이력이 남지 않는다.
- 인쇄 설정(모드, 방향, 보정값)이 저장되지 않는다.
- 한국어 문구가 코드에 박혀 있다.
- 버그: 인쇄 스레드가 선택한 프린터를 무시하고 항상 첫 번째 프린터를 쓴다(`printer/printer_thread.py:63-73`).

## 4. 이식 원칙

1. 인쇄는 기존 R600 SDK 경로를 유지한다. 편집기는 면 전체를 이미지로 렌더링해서 지금의 `R600DrawImage` / `R600DrawWaterMark` 흐름에 넘긴다. 다눌의 Windows 드라이버 인쇄, 드라이버 가로채기식 마그네틱, PC/SC 직접 호출은 가져오지 않는다.
2. 인코딩과 UV는 SDK DLL에 있는 함수(`R600MAGCardWrite`, `R600M1Card*`, `R600DrawLayerFluor` 등)로 구현한다.
3. AI 배경 제거는 "이미지 항목의 기능"으로 편집기에 통합한다. 결과 마스크는 화이트 레이어로 자동 연결한다.
4. 데이터 쪽 설계는 카드프레소를 따르고(소스, 기준 열, 인쇄 상태 기록), 사진 필드 사용성은 다눌을 따른다(레코드별 확대/위치, 누락 표시, 일괄 조정).
5. 사용자 DB를 몰래 고치지 않는다. SQL은 항상 매개변수로 넘긴다.
6. 좌표는 mm(또는 1/100mm) 한 가지로 통일하고, 경로는 문서 기준 상대 경로를 우선한다.

## 5. 로드맵

각 단계는 그 자체로 배포 가능한 단위다. 0단계와 5단계는 편집기와 독립이라 병행할 수 있다.

### 0단계: 기반 정리

- 선택한 프린터가 실제 인쇄에 쓰이도록 수정 (`printer/printer_thread.py`).
- 대기열 취소/삭제 버튼 (`printer/print_queue.py`, `ui/components/control_panels.py`).
- 프린터 상태·오류 문구 표시. `R600QueryPrtStatus`로 상태를 읽고 `R600GetErrorInfo` / `R600GetCheckStatusMsg`로 문구를 받는다. `dll/R600StatusReference`는 평문이 아니라서 직접 읽지 않는다. 급지함 비어 있음, 리본 소진, 커버 열림 등을 문장으로 보여 준다.
- 리본·필름 잔량 표시: `R600GetRbnAndFilmRemaining`.
- 인쇄 설정(모드, 방향, 위치 보정) 저장.

### 1단계: 디자인 편집기

- 문서 모델: `문서 → 면(앞/뒤) → 항목`. 항목 공통 속성은 위치, 크기, 회전, 순서, 잠금, 레이어, 인쇄 여부, 데이터 소스.
- 항목: 텍스트, 이미지, 사각형/원, 선, 바코드(1D), QR. 바코드는 인쇄 해상도로 직접 생성한다.
- 레이어: 컬러, 화이트(마스크). 이미지 항목에서 "배경 제거"를 실행하면 화이트 레이어 마스크가 생긴다.
- 편집: `QGraphicsScene` 기반 선택·이동·크기·회전, `QUndoStack` 실행취소, 정렬/동일 간격, 모눈·스냅, 눈금자, 확대/축소, 복사/붙여넣기.
- 렌더러: 면을 인쇄 해상도 이미지(컬러 + 화이트 마스크)로 출력해 기존 `printer/r600_printer.py`에 전달. 도련·위치 보정 로직은 그대로 쓴다.
- 기존 "이미지 한 장 인쇄"는 이미지 항목 1개짜리 문서로 흡수한다.
- 신규 모듈 제안: `design/model.py`, `design/items/`, `design/renderer.py`, `ui/editor/`.

### 2단계: 파일과 템플릿

- 디자인 파일: ZIP 안에 `document.json` + 이미지 + 썸네일. 버전 번호 포함.
- 최근 파일, 자동 저장 백업, 템플릿으로 저장/새로 만들기.
- 카드 규격 프리셋(CR80 등)과 사용자 지정 크기.
- (선택) 다눌 `.dnc` 가져오기. 평문 XML이라 가능하지만 단위 환산과 회전 누락 보정이 필요하다.

### 3단계: 데이터 연결

- 문서 내장 DB(SQLite): 열 추가/삭제, 형식은 텍스트, 숫자, 날짜, 시간, 목록, 사진.
- 가져오기 마법사: CSV(인코딩·구분자 자동 추정, 헤더 유무), Excel(시트 선택), 열 맞추기.
- 외부 연결: SQLite 파일, CSV/Excel 직접 읽기. Access와 ODBC는 수요가 확인되면 추가한다.
- 기준 열(행 식별용)을 사용자가 고른다. 없으면 내부 행 번호를 쓰되 사용자 파일은 고치지 않는다.
- 항목 소스: 고정값, DB 열, 열 연결(접두/접미, 빈 값이면 숨김), 인쇄 카운터, 인쇄 날짜.
- 사진 필드: 폴더 + 열 값 + 확장자 후보로 파일을 찾는다. 레코드별 확대/위치 저장, 누락 레코드 표시, 전체 일괄 조정.
- 보기: 그리드(선택 체크), 폼 + 카드 미리보기. 조건 필터와 찾기.
- 신규 모듈 제안: `data/connection.py`, `data/importers/`, `data/binding.py`, `ui/data/`.

### 4단계: 데이터 인쇄

- 인쇄 대상: 현재, 전체, 범위(`1,3,4-9`), 선택한 레코드, 조건.
- 레코드별로 렌더링해서 기존 대기열에 넣는다. 진행 표시는 "N / 전체"와 "이 레코드 건너뛰기".
- 인쇄 후 DB에 상태/횟수/날짜 기록(열은 사용자가 지정). 일괄 "인쇄 안 됨으로 되돌리기".
- 작업 이력 저장(SQLite): 작업, 카드별 결과, 오류 문구. 앱을 다시 켜도 남는다.
- 오류 정책: 중단 / 카드 배출 후 재시도(횟수 지정) / 건너뛰기.

### 5단계: SDK 기능 확장

함수 인자와 카드프레소의 호출 순서는 `r600-sdk-reference.md`에 정리했다. 실기 테스트는 아직 하지 않았다.

- UV 레이어: `R600SetLayerFluorThreshold(임계값)` → `R600SetRibbonOpt(1, 1, "180", 4)` → `R600DrawLayerFluor(x, y, w, h, 경로)`. 임계값 기본 220. 편집기 레이어에 "UV" 추가.
- K패널 분리 인쇄 옵션: `R600SetImgUtilIsNeedSet_K_ColorRibbonSplitPrint(flag)`. 앞면과 뒷면이 함께 있을 때만 켠다.
- 마그네틱: `R600CardMoveImpr(위치)` → `R600SetMagCardOpt(1)`(고보자력) → `R600MAGCardWrite(10, 트랙1, 길이1, 트랙2, 길이2, 트랙3, 길이3)` → `R600MAGCardRead`로 검증. 마그네틱 항목(트랙 1~3, 길이·문자 검증). ISO 형식만 다룬다.
- 비접촉(Mifare): `R600M1CardGetSN`, `R600M1CardPwdAuth`, `R600M1CardRead`, `R600M1CardWrite`, `R600M1CardHalt`. 인자는 확인했지만 카드프레소가 이 함수들을 쓰지 않아 참고할 호출 예가 없다. 블록 쓰기/읽기, UID를 DB 열에 기록.
- 카드별 작업 목록: 앞면 / 뒷면 / 마그네틱 / 비접촉을 개별로 켜고 끈다(인코딩만 수행 가능).
- 프린터 도구: 카드 투입, 인코딩 위치 이동, 배출, 불량 배출.

### 6단계: 부가 기능

- 다국어(한국어/영어부터), 문구를 코드에서 분리.
- 웹캠 촬영, 얼굴 인식 자동 자르기.
- 2D 바코드 추가(DataMatrix, PDF417), 1D 종류 확대.
- 작업자 계정/권한, 인쇄 감사 기록.
- 폴더 감시나 주기 조회 방식의 자동 인쇄.

## 6. 위험과 확인 필요 사항

| 항목 | 내용 | 대응 |
|---|---|---|
| SDK 함수 인자 | 87개 함수의 인자 이름·자료형은 확인했다. 모드 번호, 리본 종류 코드, 카드 이동 위치 번호의 의미는 카드프레소 호출값과 로그로 추정한 것이다. Mifare·상태 조회는 참고할 호출 예가 없다. | 실기 테스트로 값 확정. SDK 문서가 있으면 대조. |
| 마그네틱 사용 조건 | 카드 이동 위치 번호가 인코더 구성에 따라 다르다(3-in-1이면 5, 아니면 6). SDK 설정의 카드리더 모델 값과 연동된다. | `R600GetPrtOptionStatus`로 보유 프린터의 인코더 구성 확인. |
| 렌더링 품질 | 텍스트·바코드를 이미지로 넘기므로 해상도와 K패널 처리에 따라 선명도가 달라진다. | 1단계에서 실기 인쇄로 해상도와 검정 처리 방식을 먼저 정한다. |
| 범위 | 카드프레소 전체를 따라가면 끝이 없다. | 단계별로 끊어 배포하고, 6단계는 수요 확인 후 진행한다. |
| 저작권 | 두 프로그램의 코드와 자산은 보호 대상이다. | 기능만 참고해 독자 구현. 폰트·템플릿·DLL 재사용 금지. |

결정이 필요한 것:

1. 시작 순서: 편집기(1단계)부터인지, SDK 확장(5단계)이 더 급한지.
2. Access(MDB) 지원이 필요한지. 다눌 사용자를 옮겨 오려면 필요하다.
3. 다눌 `.dnc` 가져오기가 필요한지.
4. R600 SDK 문서 보유 여부. 인자는 확인했으므로 필수는 아니지만, 모드 번호와 위치 번호의 의미를 대조할 수 있다.
5. 실기 테스트에 쓸 프린터의 구성: 리본 종류(UV 패널 유무), 마그네틱·3-in-1 인코더 유무.

## 7. 분석 도구와 산출물 위치

- 설치한 도구(`D:\tools`): Ghidra 12.1.4, Temurin JDK 21, ILSpy 명령줄 9.1. 시스템 설정은 바꾸지 않았다.
- Claude Code 안의 REA 서버에서 Ghidra를 쓰려면 `GHIDRA_INSTALL_DIR=D:\tools\ghidra_12.1.4_PUBLIC`, `JAVA_HOME=D:\tools\jdk-21.0.13+9`를 등록 환경에 추가하고 재시작해야 한다.
- 카드프레소 전체를 Ghidra로 자동 분석하는 것은 16GB PC에서 메모리 부족으로 실패했다. 자동 분석 없이 불러온 뒤(`-noanalysis`) 필요한 주소 범위만 디컴파일하는 방식은 힙 3GB로 몇 분 안에 끝난다.
- 다눌 디컴파일 소스, 카드프레소 추출 리소스와 디컴파일 결과는 세션 임시 폴더에 있다. 두 프로그램의 저작물이므로 저장소에 넣지 않는다.
